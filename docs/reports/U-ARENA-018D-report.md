## Adopted Hold rule and implementation

The user selected: **automatic six-second Hold maintenance check; no Action cost**. This is recorded as adopted revision 67 in `docs/encounters/encounters-consistency-decisions-r67.md` and linked from the controlling Encounter package. The adopted rule retains the existing initial-Grapple substitution and independent Grip schedules.

- Transactional progression inserts each due check at its exact six-second boundary as a receipt-bearing native system event. Long steps resolve through their constituent committed seconds so the event joins the ordinary frozen snapshot, deterministic RNG, settlement, publication, replay, and Save/Load path.
- Check-and-schedule is serialized on the scheduler/ChoiceBook lock. Duplicate maintenance events are suppressed. An initial Grapple for the same Grip at its coincident first check continues to substitute for maintenance.
- A strict holder win maintains that Grip; a tie or loss releases only that Grip. A test also proves an ordinary Touch by the holder resolves at the same boundary, showing that automatic maintenance consumes no actor Action capacity.
- Manually declaring Hold is refused; the Arena catalog describes automatic maintenance and does not offer it as a paid Action. The Arena no longer reports a simultaneous system Hold as the player's last chosen Action.

### Narrow decisions, after independent work

The current native reservation guard rejects a second accepted Wrest on the same Object; this is an existing safety behavior, not an adopted winner rule. The adopted Wrest rule says a successful challenger takes the Object, but does not specify the result if multiple same-snapshot challengers each win. Options: (A) fail the simultaneous custody contest closed and leave the Object with its holder; no extra dice or time, but no challenger transfers it; (B) reroll the full involved contest set without advancing time until exactly one challenger wins; this enables a transfer but consumes additional deterministic RNG and needs an explicit termination/compatibility rule if rerolls keep producing multiple winners or none. No priority winner has been invented.

The willing-Touch rule allows a Touch during another Action without Multi-action only “if” the actor still has capacity. It does not define that capacity test. Options: (A) permit it only when the actor's other Action does not use the touching hand and both actor and recipient satisfy the stated stationary/motion checks; preserves a narrow opportunistic Touch; (B) require a declared Multiple-action program for any Touch concurrent with another demanding Action; simpler capacity accounting but removes the stated exception unless that exception is explicitly amended. This does not block the independently implemented no-cost Hold-maintenance rule.
