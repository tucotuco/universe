## Finding

The current architecture has pieces useful for a family constraint system: immutable Reality facts, aggregate Group counts, deterministic latent member-slot IDs, detached adult realization candidates, and an atomic one-boundary publisher. It does **not** have a family relationship model or a general transaction operation for committing relationship facts. The Being model has no native birth-date/age field. StatisticalGroup supports adult Human Being realization only; child and animal realization explicitly refuse. Thus neither historical family code nor the current Encounter pipeline can be treated as a ready-made family generator.

The recommended first implementation proof is **Alternative B, one explicitly authored parent–child edge between two already-counted Group member slots**, without creating a new member or changing group composition. This is materially smaller than generating every child through a date. It would test identity reservation, temporal constraint validation, idempotence and atomic Reality publication without assuming demographic distributions. It is only a proposed bounded proof: whether these slots represent parent and child, which time semantics apply, and the minimum temporal constraints require user approval first.

Alternative A remains the more complete later request contract: resolve all offspring of an identified adult through a specified time. It necessarily requires approved offspring/relationship semantics, a defined population scope, time/age rules, and a rule for how those offspring fit existing counts. It should not be the first implementation until those decisions are adopted.

## Proposed minimal world-only contract (for approval)

This is an interface proposal, not implementation authorization.

1. **Request:** a frozen, data-only `FamilyResolutionRequest` carries a caller-supplied idempotency key; an explicit trusted-world authority context (never a Being/observer); the Universe and optional Encounter identity; a bounded scope; requested relationship operation; `through_time` where applicable; source/provenance label; and expected Group/Reality revisions. It contains no callback, generator, mutable world reference, or observer destination.
2. **Candidate:** a detached immutable `FamilyResolutionCandidate` contains the normalized request, exact read-set/dependency token, logical identity reservations, a complete tuple of proposed objective relationship facts, any explicitly permitted Being/Group membership transitions, deterministic draw provenance if sampling was approved, and a complete write/rollback manifest. Candidate construction is pure and does not call `StatisticalGroup.member()`, alter caches, allocate authoritative IDs, mutate RNG, or update Awareness/Belief.
3. **Facts:** relationship facts should be explicit and typed rather than pointer-only: stable endpoints, relation kind/role, effective start and optional end, event/effective time as defined by an approved rule, source request key, and provenance. Validate endpoint existence/reservation, reciprocal consistency if required, acyclicity if the selected relation requires it, and all temporal constraints jointly. Do not assume “parent” means biological rather than adoptive/social.
4. **Identity:** identities are world-level and independent of names/Being materialization. Existing Group slots may be referenced only under trusted-world authority; reserve each logical identity before linking it; refuse collisions against Universe, Group, Encounter, history and prior reservation spaces. Never return latent slot identifiers through Agent-facing outputs. Stable-ID derivation and reservation namespace require approval.
5. **Population:** the candidate must prove every referenced member belongs to the Group's established composition, preserve each category and total count, and not instantiate an additional current member merely to satisfy a relationship. A later Being materialization is a separate explicit typed operation with next-boundary eligibility; no retroactive membership in the current shared snapshot.
6. **Commit:** a trusted world-only operation commits the complete Reality ledger candidate and any approved Group/Universe writes atomically under owned publication. If invoked during an active Encounter, it must be a typed world-state operation in the interval candidate/publisher, not a direct call to `realize_being()` and not a fake Action. Existing receipt issuance remains tied to real Actions; do not forge an Action receipt for generation. On any failure, preserve entity identities, collection identities, counts, Reality revisions, RNG and observer ledgers.
7. **Observation separation:** world resolution creates only objective Reality and any expressly authorized Being state. It does not create evidence, Awareness, testimony or Belief. Such consequences require a separate supported observation/effect path.
8. **Idempotence/conflict:** same request key and same normalized inputs returns the same committed facts without another mutation. Reuse of a key with different inputs, duplicate logical identities, stale dependencies, contradictions, incomplete candidate coverage, or unsatisfiable constraints refuse atomically; do not reroll to hide a contradiction.

### Randomness, order and unsatisfiable requests

The current Group's keyed `composition_rng(seed, group_id, parts...)` is a promising deterministic primitive for identity-keyed draws; the Encounter `RNGCursor` is transaction-owned and must not advance during candidate preparation. Neither mechanism defines family draws. A pure candidate may derive provisional values from an approved request/member key and publish RNG state only with commit.

Two different guarantees must not be conflated: **deterministic replay** means the same ordered requests and starting checkpoint reproduce the same result; **request-order invariance** means independent requests produce the same per-member facts even when order changes. Keyed per-subject streams can support the second for independent facts, but globally constrained sibling counts, rank assignments, or shared parent selection can couple candidates. The first proof should avoid random demographic generation. Later stochastic generation must explicitly choose which guarantee is required and test it.

If a candidate conflicts with established Reality or no assignment satisfies all constraints, return an explicit unsatisfiable/refused result with no writes and no reroll. Do not silently change dates, identity, parent role, Group counts, or an earlier fact to make it fit.

## Alternatives and tradeoffs

### A. World-only “all offspring through time t” request

The request names one adult, a time horizon, and the scope meant by “offspring.” The resolver would have to determine whether existing children are included, whether only births by `t` are generated, whether deceased offspring remain represented, and how facts outside the current Group are counted. It is the clearer eventual authoring convenience but requires more unresolved rules and potentially many facts/identities in one candidate. Existing adult identity can be an anchor; current source does not supply age, fertility, offspring distributions, or life chronology.

### B. One parent–child edge between two already-counted members of the 11-human Group — recommended first proof

An author supplies two trusted-world references to stable existing slots and one parent-role relation fact. Candidate validation confirms both slots are in the Group counts, prevents duplicates/conflicts, conserves the 11-human total, and publishes one fact atomically. This avoids generating a Being and avoids distribution rules. But the current fixture only asserts the human count; it does not establish which slots are adults/children, either individual's age, or a valid parent-child chronology. The world author must expressly anchor permitted slot IDs and approved relation time; selection must not be inferred from aggregate counts. If this proof includes a child slot without a Being, that is a logical latent slot reference, not a child Being realization.

## Decisions requiring approval

1. Is the first relation specifically **biological parent–child**, or may “parent” mean another role? Are two or more parents represented, and are parent roles ordered/typed?
2. Which times are facts: birth time, relation effective time, conception/gestation, or only an authored relationship-validity interval? What calendar and precision apply? Current Beings have no birth-date field.
3. For B, may the world author explicitly select one adult slot and one already-counted child slot from the 11-human Group, and may it assert a relationship without generated demographic samples? How are latent logical slots represented before their Beings exist?
4. For A, does “all offspring through `t`” include deceased and non-Group children? May it create historical facts outside current Group counts, or must every child map to a pre-counted slot? Is `t` inclusive?
5. Are relationship facts immutable once established, or can dated roles end/change? Which reciprocal constraints, cycle checks and conflict rules are normative?
6. Which stable identity namespace and request-idempotency contract is approved? Is reproducibility of the same request sequence sufficient initially, or is request-order invariance required for independent facts?
7. Does a world-only family-resolution operation need to run during Encounter interval publication, or may the first proof commit in an explicitly owned non-Encounter world transaction? If Encounter-bound, which existing receipt/chronology record (if any) should represent a non-Action world operation? No Action receipt should be fabricated.
8. Historical offspring/lifespan data has unverified provenance and rights and conflicting age tables. It must remain unused until selected sources are safely decoded and approved.

## Acceptance scenarios for the eventual first proof

1. A trusted-world request for the same approved parent/child slot pair produces one immutable candidate with stable endpoint IDs, a typed relation and exact source/time provenance; it creates no Being and does not mutate Reality, Group caches, observer ledgers or RNG.
2. A stale Group composition revision, missing endpoint, duplicate identity reservation, or wrong Group rejects before publication; counts, object identities and all containers remain byte/state-equivalent.
3. A candidate that contradicts an already committed parent/child fact or violates the approved chronology is refused as unsatisfiable; no arbitrary precedence, date adjustment or reroll occurs.
4. A successful atomic commit adds exactly the approved objective relation fact(s), preserves the Group's adult/child/human totals, retains all entity/container identities, and records no observer evidence or Belief change.
5. Repeating an identical idempotency key returns the same committed result without duplicate history/revision changes; reusing that key with different endpoints or time refuses.
6. An injected failure at each publication write and final consistency validation restores Reality, reservations, Group state, RNG, and Encounter state exactly; a corrected retry produces the same candidate identity/facts.
7. If a later explicit Being realization is approved, it reuses the reserved slot identity, becomes eligible only at the following Encounter boundary, does not change the current shared snapshot, and does not automatically inform any Agent.
