# Native persistence capability matrix

> Source audit for the revised U-PER-SCALE-001 full native-persistence capability. This is a live-code coverage inventory, not a completion claim. `Arena /12` means the type is admitted by the current generated-Arena checkpoint field gate; it does not imply Arena-independent support. `native_graph_snapshot` uses the closed 159-type field registry; native graph `/2` reconstructs Target rows, EntityInspection contexts, publication receipts, Disarm landing indexes, observer recipient projections, ChoiceBook lookup indexes, fatigue-frame caches and projectile interval caches from authenticated native history rather than serializing those projections twice. History `/12` adds stable recipient-store identities, while recipe `observer-recipient-facts/2` persists each binding's originating Action field and validates it on restore; recipe `/1` remains readable by matching its stable hash to saved Action references. Strict history `/1`–`/11` migrations preserve unavailable initial Entity facts as unavailable and map legacy recipient IDs only when the host binding is unique. Selected native Action, movement, combat, Group, observer and reproduction families pass full continuation scenarios; the matrix remains open for unsupported family/history readers and application Save/Load cutover. Rows are derived from the live closed field registry and checked against the current `/12` allowlist.

## Current production boundary

- Native closed-field catalog: 159 types in `src/checkpoint_fields.py` (`FIELD_ADAPTERS`).
- Executable `checkpoint_inventory._TYPES` now includes the same 159 reviewed types. `test_executable_native_type_registry_matches_all_reviewed_field_adapters` prevents type/field-registry drift; this admits the four previously omitted typed records but does not imply semantic closure or restoration readiness.
- Current production `/12` snapshot admits 104 domain types plus five structural container types via the compatibility shim `src/arena_native_snapshot.py` (`_ARENA_TAGS`); its production capture still requires a generated Arena and Arena-owned/exclusive Encounter RNG cursor.
- `/12` persistence contract is currently rooted in `src/arena_persistence.py` and `src/arena_history_segments.py`; restoration reassembles the graph and calls `arena_native_snapshot.restore()`, which binds Arena-specific progression/receipts. It is not a general native persistence API.
- `src/checkpoint_inventory.py` still advertises a non-ready diagnostic candidate; `CheckpointCandidate.require_complete()` rejects. Native Save uses explicit closed-field capture, `src/checkpoint_adapters.py` owner recipes, strict `src/native_graph_snapshot.py` graph `/2` restore, and authenticated `src/native_history.py` recording/query. The current `/2` writer excludes duplicate Target, Entity, receipt, publication, Disarm and recipient projections from the graph when their exact native-history facts and owner bindings are present; Load reconstructs typed committed receipt views before the ordinary strict inspection validators run. Shared testimony-list account order is rebound from the single authoritative append-only native list, while per-listener historical facts remain separated. Exact prior full-native graph `/1` fingerprints remain strict migration inputs. Production `/12` capture/read/write is unchanged. `src/native_persistence.py` reads accepted generated-Arena `/10`–`/12` archives through strict legacy decode plus native graph restore. With an explicit pristine-start selection of native transactional mode, `/10`–`/11` files export to native format, strict-load and continue through a legal first native Choice; generated `/12` first-Choice state also has native export/load/canonical-resave evidence. No Action is synthesized during migration. Only tested family closures may be treated as supported; full receipt-history parity, crash-recoverable history journaling and production Save/Load cutover remain open.
- History `/11` captures the true initial EntityInspection projection from the first validated pre-action transaction snapshot; `initial_entities_available` is explicit and strictly validated. Schema `/12` adds stable recipient-store identity so two same-owner BeliefLedgers remain distinct while later Actions reusing one store cannot re-key prior history. Graph recipe `observer-recipient-facts/2` preserves the exact Action-field origin and verifies that the stored binding digest names the restored recipient; `/1` descriptor migration recovers the origin from a matching saved Action reference. Collision tests reject two distinct stores claiming one binding and one reference claiming conflicting bindings. Strict host binding requires a valid stable identity; legacy role/owner-only recipient facts map only when exactly one host store is possible. `test_initial_history_precedes_first_boundary_movement_and_survives_fresh_load` checks authored position before first committed movement, then the committed boundary and strict fresh-process continuation. `test_native_save_distinguishes_same_owner_belief_ledgers` checks separate stores, a later earlier-sorting Action alias, current recipe Save/Load, a synthesized prior-recipe migration, and re-sealed forged-ID rejection. `test_native_history_v10_save_migrates_without_inventing_initial_entities` strictly migrates a `/10` native Save, verifies boundary-zero unavailability and committed query parity, continues in a fresh process, and checks canonical migrated Save→Load→Save. Legacy `/1`–`/11` history retains its historical first-receipt delta anchor and reports no boundary-zero Entity fact; it is never inferred from the restored current graph.
- “Not admitted” below means no current `/12` capture/restore evidence; no inference that the native runtime type is impossible to reach. This matrix must be upgraded with per-scenario tests as each general native family is implemented.
