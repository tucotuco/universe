## 1. User decision and required finished outcome

Deliver a **fully functional, production-quality, Arena-independent native Universe/Encounter persistence implementation** based on:

1. **Initial authoritative state** of realized entities, relevant relationships and unresolved commitments.
2. **Ordered, atomic, time-qualified property changes** (including creation/removal and changes in knowledge/realization) with explicit before/after or equivalent lossless semantics.
3. **Meaningful Events and Effects**, including failed/no-property-change Actions, causal links, simultaneous results, observer-specific facts and timeline information necessary to recover history.
4. **Complete current-state Save snapshots**, with sufficient future-relevant state to restore and continue the *same logical Encounter* without rerunning old Actions. Shared immutable definitions are preserved exactly once by content or in an integrity-checked, self-contained portable bundle.

The model must satisfy **Universe's defined and implemented requirements**, not merely the hand-authored two-Being Run/Delay/Dagger fixture. The deliverable must be exposed through ordinary native application APIs and real importable code, rather than through an example-only script or ad hoc query facade. The native implementation is the authority; **Arena is only a consumer**. Existing production save behavior and user data must remain working throughout migration.

**Acceptance is all-or-nothing against the capability matrix in §3 and the final gate in §8.** A restricted field closure, an opt-in proof, an unsupported-history disclaimer, a final-state-only replay, or a compelling architecture document **does not satisfy this assignment**. If a genuine prerequisite prevents full completion, keep U-PER-SCALE-001 ACTIVE and report the exact blocker; do not label a narrower slice accepted as the finished deliverable.

No arbitrary 45–60-minute stop condition. Finish independently feasible work in coherent, tested commits, using the smallest architecture that satisfies the complete contract. Avoid six-hour undifferentiated test sessions: run targeted tests at each milestone and broader suites only at integration gates. Report problems first, accomplishments second.

## 2. Identity, replay and rules-version policy

- **Same logical Encounter — Save/Load:** preserve literal existing Being, Object, Encounter, Action, Event, Effect, Choice, and other externally referenced logical IDs and the references between them. Never regenerate or gratuitously re-key published facts. Python object addresses are not persistent IDs.
- **Separate newly instantiated Encounter — current-version testing:** generated identifiers may differ; compare historical and simulated meaning through a validated one-to-one identity map, preserving distinct equal-valued Events/Effects, causal edges, multiplicity, order, source attribution and simultaneous grouping.
- **Replay is a test mechanism.** Current-rule deterministic re-execution validates that recorded facts match the current native simulation. It is **not** a promise that newer rule versions reproduce old decisions, rolls or outcomes. Historical playback must use the facts recorded at the time, not re-evaluate them against new rules.
- **Save/Load is not historical rerun.** A fresh process restores the authoritative current snapshot, verifies historical integrity, reconstructs required native services/indices, and continues via the normal native scheduler/evaluator/publisher. No resolving old Actions as a substitute for restoration.
- **Cross-version data:** preserve accepted legacy `/10`–`/12` saved files through tested readers and an explicit migration or coexistence strategy. Where a genuinely incompatible ruleset prevents continued simulation, reject with a precise compatibility explanation without altering the artifact. Do not silently regenerate old Beings or substitute current definitions. Do not impose cross-version deterministic replay.

(B) Formally defined but not implemented/reachable: provide a concrete extensible **record/schema and validation contract** for the defined facts, with serialized examples/round-trip tests where possible; do not invent simulation semantics or claim runtime integration. An actual missing fact needed to represent the adopted contract is a documented blocker. (C) Aspirational/undefined: explicitly label out of scope; do not invent new rules. This classification cannot be used to excuse an inconvenient but currently supported native feature.

Do **not** restrict the new core to the old Arena `_ARENA_TAGS` allowlist, to two registered Beings, or to the previous proof's closed Human/Dagger set. If the current native simulation itself restricts active participants, identify and test up to the real supported limit, and distinguish that rule/engine limitation from a persistence limitation. Preserve multiple Entities, nonparticipants, definitions and contexts without imposing the UI's two-observer contract on general native storage.

## 4. Implementation requirements — production native API, no second resolver

1. Provide cohesive native APIs for **capture, append committed history, export Save, import/validate/load Save, historical query, and continue simulation**. Use a stable, documented public contract under `src/`, not `examples/` as the authoritative implementation. The headless CLI/examples exercise these APIs but own no duplicate persistence rules.
2. **Atomic recorder:** observe the native transaction's validated, actually committed results, not merely a post-step guess. Store a commit only after publication succeeds; rejected/rolled-back/exceptional attempts leave state, RNG, current snapshot/journal and prior Saves untouched. Include event/effect causality, observation evidence and all relevant state changes even when no physical Object changes. A one-second simultaneous batch is one atomic commit with independently traceable causes.
3. **Complete history without per-second state snapshots:** retain initial state, changes, and meaningful Events once. Preserve time and any genuinely time-dependent facts. A legal no-change interval may be represented as compact boundary metadata or an equivalent contiguous span if all time-based semantics and queries remain exact. Avoid storing `TargetIntervalRecord`, `CommittedBoundaryRecord`, fatigue projections and other full historical state solely as repetitive persistence payloads; reconstruct required views on demand.
4. **Native historical read compatibility:** all existing implemented history consumers must continue to yield semantically equivalent results after Load. Adapt consumers or provide verified lazily derived views; do not manufacture a persistent copy of the old runtime graph or silently disable APIs. Strict native validation and rule invariants must remain enforceable from the new record.
5. **Complete resumable snapshot:** includes all authoritative current state needed for *any presently legal next Action*, not only the next Action selected by a fixture: pending/reserved Choices and Actions, registration/queue state, interrupted workflows, time, conditions, fatigue, locations, Object relationships, observer knowledge, unresolved commitments, and RNG. No old-Action re-evaluation. Reconstruct only proved process-local locks/caches/anchors and verify references.
6. **Portable, inspectable, bounded files:** use a canonical, documented, self-contained file/archive with versioned manifest, current snapshot, immutable definition records, initial state and ordered event/delta history. Include checksums/cross-reference validation and strict limits for entry sizes, count, total decoded bytes, nesting, type allowlist, and resource use. Avoid arbitrary pickle or executable deserialization, path traversal, compression bombs, ambiguous duplicate keys and unbounded decompression. Preserve old Saves; do not depend on a pinned local checkout to supply missing serialized definitions if portable loading is promised.
7. **Application integration:** connect the successful new native persistence path to the normal production Save/Load interfaces, including Arena as a consumer, **only after** the general native gate and migration tests pass. Do not leave it permanently as an opt-in demonstration. Prefer a controlled dual-reader/cutover strategy: keep the old `/12` path available until all accepted save cases are covered and tested; don't delete working legacy readers. Avoid routine manual browser automation; use API/HTTP tests and one focused UI integration smoke check at the final cutover.
8. **No unrelated rule rewrites:** do not change combat eligibility, Action outcomes, perception authorization, world generation, RNG semantics or adopted geometry to make a persistence test pass. Fix real engine/persistence defects when demonstrably necessary and directly scoped; document any rule gap precisely.

## 5. Mandatory end-to-end test portfolio (headless first)

Implement a reproducible native fixture/scenario runner that can author legal starting conditions and Action declarations **without Arena session/controller/server, browser or `npcgen`**, then execute real native `Encounter.step()` and transaction/publication APIs. It should be suitable for future Action development and not be tied to one hardcoded sequence. Use existing definitions and provide source-linked scenarios; don't mutate live committed state to force outcomes.

**Acceptance tests must cover the actual capability matrix**, with representative positive, negative, interrupted and simultaneous cases for each implemented family. The minimum portfolio additionally includes:

1. **History fidelity:** initial state plus committed change/Event history reconstructs all supported authoritative properties and observer-specific evidence at **every checked boundary**. Query time points before, at and after movement, injury, equipment/ownership changes, an observation, a failed/no-change Action, a pending Action, an interrupted Action, and simultaneous effects. Preserve Event/Effect identities and causal multiplicity within one Encounter.
2. **Native continuation:** multiple fresh OS processes load complete Saves made at differing boundaries (including an unresolved pending Action/Choice, a settled history and a changed RNG stream), continue with ordinary native Actions and produce the same outcomes/history/current state as uninterrupted control using the same current rules. If a legacy API expects historical receipts, prove compatible queries without persisting redundant per-boundary state graphs.
3. **Current-version replay validation:** historical playback (no Action resolution) and independently instantiated native re-execution of recorded legal declarations agree on state, Event/Effect semantics, causal groups, knowledge and RNG, allowing validated generated-ID remapping only between distinct Encounters. This is a **test**, not cross-rule-version compatibility.
4. **Defined-but-not-implemented contracts:** serialize, validate and reconstruct the defined record shapes available today; distinguish schema coverage from native behavioral coverage. Report formal-spec gaps without inventing behavior.
5. **Corruption and security:** reject malformed, missing, duplicated, out-of-order, truncated, conflicting, stale, incompatible and adversarial records; bad definitions, invalid IDs/references, duplicated identical Effects, invalid causal order, forged observer evidence, malformed permissions, incorrect preimages, oversized segments and aborted writes. Test transactional refusal with live state/previous complete Save unchanged.
6. **Scale and efficiency on controlled fixtures:** compare new vs existing production persistence on the **same** source scenario where supported: baseline, >=64 lawful resolved combat Actions or a technically justified equivalent, hundreds of quiet boundaries, and 2/20/200 realized registry Beings as native contracts allow. Measure snapshot/definitions/event-history bytes, change counts, total archive bytes, peak RSS, Save/Load/query timings and dependence on elapsed time. No claims based on unrelated fixtures; no fabricated active 200-combatant Encounter. Show why retained history scales with *new information and necessary time facts*, rather than with repeatedly captured graph closure.
7. **Production integration and compatibility:** old `/10`–`/12` accepted fixture files load through supported migration/coexistence, ordinary native Save→Load→Save is canonically equivalent, and Arena Save/Load works through automated session/HTTP checks plus a final focused UI smoke if feasible. Never regress or overwrite users' stored Saves. Test private observer views after restoration.
8. **Regression ownership:** run direct new tests, affected native scheduling/publication/inspection/observer/field-realization tests, persistence/compatibility tests and broader integration gate appropriate to a high-risk persistence cutover. Record exact commands, counts and durations. Investigate the earlier 55 pass / 4 error / 2 failure transactional-progression result against a clean baseline before attributing it to existing failures; do not weaken tests to suppress it.

**Crucial:** A passing Run/Delay/Dagger demo, fixed 9-boundary replay, or fixed 2-Being full-state projection alone is **insufficient**. Add scenarios to cover all currently implemented persistent contracts; keep every uncovered row visible in the capability matrix and block overall acceptance until closed.
