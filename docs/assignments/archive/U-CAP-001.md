## Integrated completion requirements

### 1. General Multiple-action program

- Build on the **already implemented** native ordered Choice programs, 1–4 Action priority/penalty table, overlap-based shared resource accounting, repeating programs, abort/interruption, and checkpoint restoration. Reuse those primitives instead of introducing a separate browser-side scheduler.
- Extend the generated Arena beyond the existing hard-coded two-Touch and Grapple + Break-hold demonstrations to a general, observer-authorized composer for **all currently eligible supported Action combinations**. Show component order, intended targets/handles, execution timing, per-component priority, defense/ability/skill resources and rejection reasons. Do not offer an Action the native engine cannot legally instantiate.
- Prove mixed-duration overlapping and sequential components, independent legitimate simultaneous effects, resource/hand conflicts, fixed penalties, scheduling across boundaries, action completion, cancellation, repeat-until-abort behavior and no undesired RNG use on rejected declarations. Keep no-cost automatic Hold-maintenance and the revision-68 willing-Touch exception distinct from declared demanding Actions.
- Make a reproducible ordinary generated-Arena session through the shipped controls without mutating private fixture state to force results. Test ordinary HTTP/session controls and attempt actual browser interaction when access allows; distinguish these evidence levels.

### 2. Adopted Delay and conditional Ready

- Read the **current controlling adopted** Delay and Ready rules before designing. Inventory what the native Choice/Action model already supports. Implement their legally specified declaration, timing, retention/trigger, interruption/abort and overlap behavior where the rules provide unambiguous authority. In particular, do not equate simply advancing time or existing Draw with the Delay/Ready Actions.
- If a specific trigger evaluation, indefinite retention, priority or consequence is genuinely undefined, isolate that case as an explicit bounded unimplemented branch with a minimal user decision request. Finish all independently determined branches and the general composer first. Do **not** invent physical reactions, free Actions, hidden perception, or a new conflict priority to create an apparently complete feature.

### 3. Persistence, faults and integration

- Native, generated HTTP/session and fresh-OS-process Save/Load for an accepted not-yet-started program, a running mixed-duration program, an interrupted/aborted program and a repeat cycle. Reconstructed Action IDs, time offsets, priorities, observer evidence and private RNG ownership must agree with native committed history; loading never regenerates Beings.
- Test same-boundary consequences, conflicting reservations, invalid/unknown targets, partial resource conflicts, retained defenses, coincident no-cost maintenance, and injected publication/rollback fault cases where shared transactional primitives are affected.
- Include adjacent contact/defender/Disarm/Wrest regressions where this touches their shared Choice/Action machinery. Do not run the roughly hour-long full suite on every small increment; use focused cohorts and run broader regression only at a meaningful integration boundary. Report exactly what passed and failed, including genuine baseline failures and browser limitations.
